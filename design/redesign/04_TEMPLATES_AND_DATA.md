# 템플릿 · 플랜 · 데이터 설계

근거: `논리적 사고 훈련 시스템 구조안.pdf` (공통 FLOW, 목적별 모듈 A~G, 통합 템플릿 STEP 1~10, 난이도 Level 1~8, 일·주·월 루틴)

---

## 1. 기본 원리 — 프레임워크를 늘리지 않는다

> "새로운 프레임워크를 계속 추가하는 것이 아니라, 동일한 공통 FLOW를 다양한 문제·난이도·결과물에 반복 적용하는 것" — PDF §13

따라서 시스템에 존재하는 것은 **단계 10개 하나뿐**이고,
템플릿은 그중 **어떤 단계를 켜고 끄느냐**의 조합일 뿐이다. 별도 엔진을 만들지 않는다.

```
Stage (10개, 고정, 순서 불변)
  └ Template  = 켜진 Stage의 부분집합 + 질문 세트 + 도움 정도
      └ Case  = Template을 특정 주제에 적용한 실제 기록
```

---

## 2. 단계 정의

| # | key | 표시명 | 인포그래픽 |
| ---: | --- | --- | --- |
| 1 | `context` | 목적·맥락 이해 | 맥락 카드 |
| 2 | `observation` | 현상 관찰 | 사실·해석·미확인 보드 |
| 3 | `problem` | 문제 정의 | 한 줄 문제 정의 조립 바 |
| 4 | `structure` | 문제 분해·구조화 | 로직 트리 |
| 5 | `hypothesis` | 가설 설정 | 가설 카드 덱 |
| 6 | `evidence` | 근거 수집·검증 | 검증 매트릭스 |
| 7 | `decision` | 대안 비교·의사결정 | 비교 스코어 표 |
| 8 | `design` | 해결안 설계·실행 | 사용자 FLOW 체인 |
| 9 | `result` | 결과 평가 | Before/After 지표 카드 |
| 10 | `reflect` | 결론 전달·회고 | 논리 체인 한 장 |

**순서는 바꿀 수 없다.** 앞 단계의 응답이 뒤 단계 질문의 재료로 들어가기 때문이다.
(예: 4단계 로직 트리의 루트 노드 = 3단계에서 완성한 한 줄 문제 정의)

## 3. 목적별 모듈 (훈련 시작 01번 시트)

PDF의 모듈 A~G를 화면 선택지로 옮긴 것.

| 모듈 | 선택지 문구 | 켜지는 단계 | 시간 |
| --- | --- | --- | --- |
| A | 문제를 정의하고 싶어요 | `observation` `problem` | 15분 |
| B | 생각을 구조화하고 싶어요 | `structure` (심화 질문 6개) | 20분 |
| C | 가설과 검증을 연습하고 싶어요 | `hypothesis` `evidence` | 25분 |
| D | 의사결정을 연습하고 싶어요 | `decision` `design` | 20분 |
| E | 논리적인 글을 쓰고 싶어요 | `context`~`evidence` + `reflect` | 60분 |
| F | 면접 답변을 준비하고 싶어요 | `context` `problem` `structure` `hypothesis` `reflect` | 30분 |
| G | 지난 프로젝트를 회고하고 싶어요 | `result` `reflect` | 25분 |
| — | 포트폴리오를 만들고 싶어요 | 10단계 전부 | 4주 |

모듈 B처럼 단계가 하나뿐인 경우, **그 단계의 질문 수를 늘려** 깊이를 만든다. 단계를 늘리지 않는다.

## 4. 템플릿 프리셋 (훈련 시작 03번 시트)

| 프리셋 | 단계 | 시간 | 언제 |
| --- | --- | --- | --- |
| **하루 한 단계** | 1~2개 (요일별 지정) | 20분 | 매일 |
| **주간 전체 흐름** | 7개 (`context`~`evidence`, `reflect`) | 60분 | 주 1회 |
| **월간 포트폴리오** | 10개 전부 | 4주 | 월 1회 |
| **면접 케이스** | 5개 (압축) | 30분 | 필요할 때 |

프리셋을 고른 뒤에도 **단계 칩 10개를 직접 켜고 끌 수 있다.** 프리셋은 출발점일 뿐이다.

### 도움 정도

| 수준 | 동작 |
| --- | --- |
| 안내 많이 | 질문마다 예시와 힌트가 기본 노출 |
| 보통 (기본) | 요청할 때만 힌트. 예시는 오른쪽 패널에 접혀 있음 |
| 거의 없이 | 단계 종료 시 점검만 |

같은 단계를 3회 이상 수행하면 **한 칸 낮추자고 제안**한다. 반복할수록 도움을 줄이는 것이 학습 목표다.

## 5. 훈련 플랜

### 5.1 하루 — 한 단계 집중 (20~30분)

| 요일 | 단계 | 산출 |
| --- | --- | --- |
| 월 | `observation` `problem` | 한 줄 문제 정의 1개 |
| 화 | `structure` | 로직 트리 1개 |
| 수 | `hypothesis` `evidence` | 가설 3개 + 검증 지표 |
| 목 | `decision` | 대안 비교표 1개 |
| 금 | `reflect` | 결론 중심 짧은 글 |

매일 전체를 돌지 않는다. 부담이 줄고 약한 단계가 반복된다.

### 5.2 한 주 — 전체 흐름 한 바퀴 (60분)

주제 하나를 골라 `context` → `evidence` 를 통과하고 **800~1,200자 분석 글**로 마무리.
끝나면 질문 저장소에 좋은 질문 2개를 남긴다.

### 5.3 한 달 — 포트폴리오 한 건

| 주차 | 범위 |
| --- | --- |
| 1주 | `context` `observation` `problem` |
| 2주 | `structure` `hypothesis` `evidence` |
| 3주 | `decision` `design` |
| 4주 | `result` `reflect` + 문서화 |

### 5.4 진행 상태 표시

- 스트릭보다 **"이번 주에 통과한 단계"**를 센다. 연속 기록 압박을 만들지 않는다.
- 성장 지표는 근거를 함께 보여준다. 예: "3주 전보다 `structure` 소요 시간 12분 → 7분"
- **사용자 간 순위나 점수는 만들지 않는다.** 훈련이 점수 따기로 변질된다.

## 6. 예시 시스템

사용자가 막막해하는 순간의 주력 대응. 예시는 **분야 × 문제 유형 × 단계** 세 축으로 색인한다.

```
Example {
  id
  sector:      '커머스' | '핀테크' | '콘텐츠' | 'B2B SaaS' | '플랫폼' | 'HR·교육'
  problemType: '지표 하락' | '신규 기능' | '우선순위' | '운영 반복' | '지표 설계' | '실험 해석'
  stage:       StageKey
  role:        'PM' | '서비스기획' | '데이터분석' | 'DS' | '개발'
  level:       1..8            // PDF §10 난이도
  content:     구조화된 예시 (해당 단계의 인포그래픽 형태와 동일)
  why:         "왜 이렇게 했는가" 한 문장
  source:      '공개 자료' | '가상 설정'
}
```

**노출 규칙**

- 예시는 **입력란에 채우지 않는다.** 오른쪽 패널에 `참고용` 배지와 함께 별도로 놓는다.
- 사용자가 한 글자라도 쓴 뒤에 "예시 보기"가 활성화된다. 먼저 쓰고 나서 비교하는 순서를 지킨다.
- 예시마다 `why` 한 줄을 붙인다. 형태만 베끼고 이유를 놓치는 것을 막는다.
- 한 단계에 최대 2개만 보여준다. 더 많으면 고르는 데 시간을 쓴다.

**초기 확보 범위** — 6 sector × 3 problemType × 4 핵심 stage = 72개.
전 단계를 다 채우기보다 `problem` `structure` `hypothesis` `evidence` 네 단계를 먼저 채운다. 여기서 가장 많이 막힌다.

## 7. 오늘의 이슈

주제 선택의 두 번째 경로. 주 2~3건 갱신.

```
Issue {
  title            문제 형태의 제목 (해결책을 넣지 않는다)
  summary          2~3문장 상황
  sector, problemType
  premises[]       { text, status: '공개 자료' | '가상 설정' | '확인 필요' }
  toValidate[]     검증이 필요한 정보
  sources[]        공개 출처 링크와 기준 시점
  suggestedTemplate
}
```

**지켜야 할 선**

- 검증되지 않은 기업 내부 수치를 사실처럼 쓰지 않는다. `가상 설정` / `내부 수치 없음` 배지로 구분한다.
- 특정 기업의 공식 과제로 오해될 표현을 쓰지 않는다.
- 오래된 자료에는 기준 시점을 표시한다.
- 최소 두 가지 이상의 합리적 접근이 가능해야 한다. 정답이 하나면 훈련이 안 된다.

## 8. 저장소 데이터 모델

### 8.1 관찰 저장소 (Insight)

```
Insight {
  id
  text            두 줄 이내 권장
  kind            'fact' | 'interpretation'      // 이 구분이 핵심 훈련
  source          '일상' | '수업' | '뉴스' | '업무' | '프로젝트'
  tags[]
  createdAt
  relatedIds[]    유사 기록 묶음 → "비슷한 기록 3회" 배지의 근거
  promotedTo      Case.id | Question.id | null
}
```

**유사 기록 묶기** — 초기에는 태그·키워드 일치로 충분하다. 임베딩은 나중 문제다.
**반복 횟수가 곧 문제의 후보 순위**다. 세 번 적은 것이 진짜 신경 쓰이는 문제다.

### 8.2 질문 저장소 (Question)

```
Question {
  id
  text
  stage           StageKey        // 어느 단계에서 쓰는 질문인가
  origin          'user' | 'coach' | 'preset'
  starred         boolean
  usedCount       몇 번 실제로 꺼내 썼는가
  createdAt
}
```

- 작업 화면 오른쪽 패널은 **현재 단계의 질문만** 보여준다.
- 즐겨찾기한 질문은 해당 단계 진입 시 자동으로 상단에 뜬다.
- 코치가 던진 질문 중 사용자가 유용하다고 표시한 것이 자동으로 여기 쌓인다.

### 8.3 사고 케이스 (Case)

```
Case {
  id, title
  templateId, enabledStages[]
  topicSource     'own' | 'issue' | 'sector' | 'insight'
  originInsightId?
  steps: {
    [stageKey]: {
      mode          'guided' | 'free'
      answers       { [questionKey]: value }     // 도식의 원천 데이터
      versions[]    { content, createdAt, reason? }   // 덮어쓰지 않고 쌓는다
      coachLog[]    { message, decision: 'applied'|'rejected', at }
      status        'empty' | 'draft' | 'done'
      checks[]      { rule, level: 'ok'|'warn', message }
    }
  }
  createdAt, updatedAt
}
```

**설계 규칙**

- 도식은 별도 저장하지 않는다. `answers`로부터 매번 그린다. 그래야 원본과 그림이 어긋나지 않는다.
- 수정은 덮어쓰지 않고 `versions`에 쌓는다. 틀린 가설과 바꾼 이유가 이 서비스의 자산이다.
- 코치 피드백을 **거절한 기록도 남긴다.** 채택률이 100%면 오히려 경고 신호다.

### 8.4 결과물 (Output)

```
Output {
  id, caseId
  type      'portfolio' | 'post' | 'interview' | 'plan_doc' | 'blog'
  sections[] {
    heading
    body
    traces[]      { stageKey, versionIndex }   // 문장 → 원본 역추적
    edited        사용자가 직접 고쳤는가
  }
  stale     원본이 바뀐 뒤 재생성하지 않았는가
  visibility 'private'(기본) | 'link' | 'public'
}
```

- 원본에 없는 성과·역할·수치를 생성하지 않는다.
- `traces`가 비어 있는 문장은 생성하지 않는다. 근거 없는 문장이 섞이는 것을 구조적으로 막는다.
- 원본을 고치면 `stale = true`. 사용자가 확인 후 갱신한다.

## 9. 점검 규칙 (코치가 짚는 것)

PDF §12-5단계의 논리 점검 항목을 실행 가능한 규칙으로 옮긴 것.
**전부 경고이며 차단하지 않는다.**

| 단계 | 규칙 | 메시지 예 |
| --- | --- | --- |
| `problem` | 문제 문장에 해결책 어휘 포함 | "‘~를 추가해서’는 해결책입니다. 문제 문장에서 빼면 대안을 넓게 볼 수 있습니다" |
| `problem` | 5칸 중 미입력 존재 | "‘어떤 상황에서’가 비어 있습니다" |
| `observation` | 한 항목에 사실과 해석 혼재 | "이 문장은 관찰과 추정이 붙어 있습니다. 두 줄로 나눠보세요" |
| `structure` | 가지 2개 이하 / 6개 이상 | "가지가 2개입니다. 3~5개가 다루기 좋습니다" |
| `structure` | 가지 간 키워드 중복 | "‘상품·공급’이 ‘첫 주문 경험’과 겹칠 수 있습니다" |
| `hypothesis` | 가설 3개 미만 | "가설이 하나면 그 하나에 고정됩니다" |
| `hypothesis` | 백업 가설 없음 | "전부 틀렸을 때 남는 가능성을 하나만 적어두세요" |
| `evidence` | 판단 기준 미입력 | "무엇을 보면 이 가설을 접겠습니까?" |
| `decision` | 대안 2개 이하 | "대안이 하나면 비교가 아니라 확인입니다" |
| `decision` | 비교 기준이 대안마다 다름 | "대안별로 다른 기준을 쓰고 있습니다" |
| `reflect` | 인접 단계 간 참조 없음 | "근거에서 대안으로 넘어가는 구간이 이어지지 않습니다" |

규칙은 전부 **사용자가 쓴 내용에만** 적용한다. 쓰기 전에는 아무것도 판단하지 않는다.

## 10. 구현 순서 제안

| 순서 | 범위 | 이유 |
| ---: | --- | --- |
| 1 | 단계 3~4 (`problem` `structure`) + 질문 카드 + 두 개의 인포그래픽 | 여기가 가장 많이 막히고, 여기서 효과를 못 보면 나머지도 안 된다 |
| 2 | 관찰 저장소 + 두 줄 캡처 | 재료가 없으면 훈련 자체를 시작 못 한다. 캡처는 가장 싸게 만들 수 있다 |
| 3 | 나머지 단계 확장 (같은 질문 카드 엔진 재사용) | 1번에서 검증한 패턴을 복제 |
| 4 | 코치 점검 규칙 (§9) | 규칙 기반으로 먼저. LLM은 그다음 |
| 5 | 케이스 맵 + 결과물 변환 | 여기서 지불 의사가 생긴다 |
| 6 | 질문 저장소 · 플랜 · 성장 지표 | 반복 사용자가 생긴 뒤에 의미가 있다 |

§9의 점검 규칙 대부분은 **LLM 없이 문자열·개수 검사로 구현할 수 있다.** 초기 비용을 크게 낮출 수 있는 지점이다.
LLM은 "더 넓게 보고 싶어요" 버튼처럼 열린 질문을 만드는 데만 쓴다.
