B2B SaaS · 개인 분석 프로젝트 · 4주 · 공개 자료와 가상 설정 기반

1. 배경과 목적

도입 3개월 차 계정의 갱신 판단이 90일 시점에 이뤄지기 때문에, 그 전에 팀 단위 사용이 만들어져야 합니다.

2. 관찰한 현상

  • 도입 후 30일 안에 핵심 기능을 한 번도 쓰지 않은 계정이 48%
  • 온보딩 이메일 열람률은 62%로 낮지 않음

3. 문제 정의

도입 담당자가 팀에 기능을 전파하려 하지만 설명할 자료가 없어 혼자만 쓰다가 멈춥니다. 자료를 만들 시간이 없다는 것이 인터뷰에서 반복해 나온 이유였습니다.

4. 문제 구조

사용자 유형을 기준으로 도입 담당자 · 팀원 · 관리자 셋으로 나누고, 각 유형의 첫 사용 시점을 별도 지표로 두었습니다. 유형별로 막히는 지점이 다르다는 것이 이 분해의 전제입니다.

5. 가설과 검증

  • 전파 자료 부재 — 인터뷰 6건 중 5건에서 언급, 지지
  • 초대 흐름 마찰 — 초대 시도 후 완료율 41%, 지지
  • 담당자 1인 의존 — 계정 규모와 무관하게 나타나 기각

6. 대안 비교와 결정

세 가지 대안을 사용자 효과 · 구현 난이도 · 리스크로 비교해 팀 초대 흐름 개선을 골랐습니다. 단기간에 지표로 확인할 수 있다는 점이 결정적이었습니다.

7. 한계

비교 기준에 비용을 넣지 않았습니다. 세 대안의 개발 공수를 같은 척도로 환산하지 않아, 난이도 판단이 정성적인 수준에 머물렀습니다. 다시 한다면 비교표를 만들기 전에 기준부터 확정하겠습니다.

확인

이 프로젝트는 실행 전 단계입니다. 성과 수치가 아니라 검증 계획과 성공 기준을 제시합니다. 실제 실행 결과처럼 읽히는 문장은 자동으로 표시됩니다.

서비스 분석 글 1,050자

온보딩은 성공했는데 왜 아무도 안 쓸까

이메일 열람률 62%는 나쁜 숫자가 아닙니다. 그런데 30일 안에 핵심 기능을 한 번도 쓰지 않은 계정이 절반에 가깝습니다. 온보딩이 실패한 게 아니라, 온보딩이 끝난 자리에서 무언가 멈춘다는 뜻입니다.

인터뷰를 해보니 도입 담당자들은 대체로 제품을 이해하고 있었습니다. 막힌 곳은 그다음이었습니다. 팀에 설명할 자료를 스스로 만들어야 했고, 그 시간이 없어 혼자 쓰다가 멈췄습니다.

이 문제를 사용자 유형으로 나눠보면 도입 담당자, 팀원, 관리자가 각각 다른 지점에서 멈춥니다. 담당자는 전파 자료에서, 팀원은 초대 링크에서, 관리자는 성과 확인에서 멈춥니다. 세 개를 하나의 “활성화율”로 묶어 보면 어디를 고쳐야 할지 보이지 않습니다.

이 글은 사고 기록 10단계에서 자동 구성한 뒤 직접 다듬은 것입니다.

상황

B2B 제품의 갱신율을 보다가, 도입 3개월 차 계정 중 절반이 핵심 기능을 한 번도 쓰지 않았다는 걸 발견했습니다.

제가 정의한 문제

기능을 모르는 게 아니라, 도입 담당자가 팀에 전파할 자료가 없어서 혼자 쓰다 멈추는 문제로 정의했습니다. 온보딩 열람률이 62%로 낮지 않았기 때문에 인지 문제로 보지 않았습니다.

접근 방식

사용자를 도입 담당자·팀원·관리자로 나눠 각각 어디서 멈추는지 따로 봤습니다. 원인 가설 세 개를 세우고 초대 로그와 인터뷰로 검증했는데, 담당자 역량 문제라는 가설은 계정 규모와 무관하게 나타나서 기각했습니다.

결과와 배운 점

실행 전 단계라 성과는 없고 검증 계획까지 만들었습니다. 돌아보면 대안을 비교할 때 비용 기준을 빼먹은 게 가장 아쉽습니다. 기준을 먼저 정하고 표를 만들어야 한다는 걸 배웠습니다.

해결하려는 문제

제안

  • 첫 로그인 직후 팀 초대 단계를 흐름에 넣습니다
  • 역할별 시작 가이드 3종을 제품 안에서 바로 공유할 수 있게 합니다
  • 7일간 초대가 없는 계정에 리마인드를 보냅니다

성공 기준

  • 30일 내 2인 이상 활성 계정 비율 28% → 45%
  • 가드레일: 초대 메일 스팸 신고율 0.3% 미만 유지

검토하지 않은 것

세 대안의 개발 공수를 같은 척도로 환산하지 않았습니다. 착수 전 확정이 필요합니다.

기술 블로그 문제–탐색–검증–학습

가설 하나를 기각하고 나서야 문제가 보였다

처음에는 담당자 역량 문제라고 생각했습니다. 제품을 잘 아는 사람이 있는 계정은 잘 쓰고, 없는 계정은 못 쓴다는 그림이 자연스러웠으니까요.

그런데 계정 규모와 상관없이 같은 비율로 나타났습니다. 이 숫자를 보고 나서 가설을 접었고, 그때부터 “누가 못 쓰나”가 아니라 “어디서 멈추나”로 질문이 바뀌었습니다.

질문이 바뀌자 분해 기준도 바뀌었습니다. 계정 규모가 아니라 사용자 역할로 나눴고, 세 역할이 각각 다른 지점에서 멈춘다는 게 보였습니다.

게시 전 확인

기업명, 실제 계정 수치, 인터뷰 대상자 정보가 포함되어 있는지 확인합니다. 기본 공개 범위는 비공개이며, 공유 링크는 언제든 철회할 수 있습니다.

변환은 원본에 있는 것만 씁니다. 성과, 역할, 수치를 새로 만들지 않습니다. 원본을 고치면 변환된 문서에 “원본이 바뀌었습니다” 표시가 붙습니다.
