참고용맥락 카드

목표를 “활성화율 개선”이 아니라 “갱신 판단 시점 전에 팀 사용 만들기”로 적었습니다.

목표에 기한이 들어가면 대안의 우선순위가 자동으로 정해집니다.

참고용사실 · 해석 분리

해석 결제 단계가 복잡해졌을 가능성이 있다

“결제가 복잡해서 이탈이 늘었다”는 한 문장은 관찰과 가설이 붙은 형태입니다.

참고용한 줄 문제 정의

중고 거래 경험이 적은 초보 판매자가 첫 상품을 등록하면서 적절한 판매 가격을 정하려 하지만, 가격을 판단할 기준이 없어 등록을 중단한다.

“가격 추천 기능이 없어서”라고 쓰면 해결책이 문제 안에 들어갑니다.

참고용프로세스 기준
  • 전환율이 낮은 이유
    • 유입 단계
    • 폼 입력
    • 인증

순서로 나눴기 때문에 가지끼리 겹치지 않습니다.

참고용백업 가설

“신규 사용자의 낮은 재주문율은 서비스 내부 경험이 아니라 지역별 공급 부족에서 나올 수 있다”

백업 가설은 대개 내가 못 바꾸는 쪽에 있습니다. 먼저 배제해야 시간을 아낍니다.

참고용데이터 없이 검증 설계

필요한 데이터 / 확보 방법 / 대상 사용자군 / 관찰 기간 / 채택 기준 / 틀렸을 때 다음 행동

“데이터가 없어 검증 못 했다”에서 끝내지 않고 여섯 칸을 채우는 것이 훈련입니다.

참고용결론 표현

“A안을 우선 적용하겠습니다. 기준은 사용자 영향 · 구현 난이도 · 검증 속도 셋이었고, A안은 단기간에 구현되고 지표로 확인되며 실패해도 비용이 낮기 때문입니다.”

결론 → 기준 → 이유 순서. 기준을 밝히면 반박이 논쟁이 아니라 검토가 됩니다.

참고용설계 순서

문제 → 사용자 행동 변화 목표 → 핵심 기능·정책 → 사용자 FLOW → 화면·데이터·운영 → 실행 계획

기능부터 적으면 왜 그 기능인지가 사라집니다. 행동 변화를 먼저 씁니다.

참고용결과가 없는 프로젝트

검증 계획 / 예상 결과 / 성공 판단 기준 / 실패 시 다음 액션 / 추가 확인 데이터

실행 전이어도 이 다섯 개를 쓰면 “계획”으로 정직하게 보여줄 수 있습니다.

참고용회고 질문

결과가 아니라 사고 과정을 묻는 질문이라 다음 케이스에 그대로 쓸 수 있습니다.
