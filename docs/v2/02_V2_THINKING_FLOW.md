# Thinking Flow V2 — 10단계 사고 FLOW

## 1. 역할

이 문서는 10단계 학습 흐름의 단일 개념 기준이다. 실제 질문 문구와 예시는 `03_V2_STAGE_TEMPLATES.md`, AI 행동은 `06_V2_AI_COACH.md`, 저장 모델은 `09_V2_DATA_MODEL.md`를 따른다.

모든 예시는 “오프라인 상품 체험을 앱 탐색·구매로 연결하는 서비스 개선”이라는 가상 Practice Case를 사용한다. 공개 정보와 가정을 바탕으로 사고 구조를 보여줄 뿐, 올리브영의 실제 고객 행동·내부 성과나 정답을 주장하지 않는다.

## 2. 단계 연결 원칙

- 이전 단계 산출물은 다음 단계의 입력이지만 언제든 다시 수정할 수 있다.
- 이동은 완료를 뜻하지 않으며 미완료 상태에서도 Soft Gate 후 이동할 수 있다.
- 각 단계는 자유 작성과 구조화 입력을 지원한다.
- AI는 사용자 작성 후 누락·혼재·근거 부족·논리 공백을 점검한다.

## 3. 단계별 기준

### 1. `context` — 목적·맥락 이해

- **목적**: 누가, 왜, 어떤 범위에서 이 문제를 다루는지 정한다.
- **쉬운 설명**: 문제를 풀기 전에 이번 일이 무엇을 위한 것인지 경계선을 긋는 단계다.
- **핵심 질문**: 해결 목적은 무엇인가? 요청자는 누구인가? 범위와 제약은 무엇인가?
- **왜 필요한가**: 목적과 범위가 없으면 이후 관찰과 해결안이 서로 다른 문제를 향한다.
- **이전 단계와 관계**: Case가 제공한 문제 상황과 업무 요청을 비판적으로 읽는 시작점이다.
- **다음 단계 산출물**: 목적, 이해관계자, 범위, 알려진 제약과 미확인 전제.
- **자주 발생하는 오류**: 해결 기능을 목적처럼 쓰기, 미검증 가정을 확정 사실로 쓰기, 범위를 무한히 넓히기.
- **추천 프레임워크**: 5W1H, Project Brief, 이해관계자 지도.
- **AI 점검 관점**: 목적과 수단의 혼재, 암묵적 전제, 범위 누락.
- **포트폴리오 연결**: Case 개요, 배경과 목적, 내 역할.

### 2. `observation` — 현상 관찰

- **목적**: 관찰된 사실, 해석, 아직 모르는 것을 분리한다.
- **쉬운 설명**: 본 것과 내가 추측한 것을 다른 칸에 놓는 단계다.
- **핵심 질문**: 무엇을 직접 확인했는가? 무엇이 해석인가? 어떤 정보가 더 필요한가?
- **왜 필요한가**: 인상이나 추측을 현상으로 확정하면 잘못된 문제를 풀 수 있다.
- **이전 단계와 관계**: `context`에서 정한 범위 안에서 관찰 대상을 선택한다.
- **다음 단계 산출물**: 관찰 목록, 출처, 해석 목록, 정보 공백.
- **자주 발생하는 오류**: “고객은 불편해한다”처럼 근거 없는 일반화, 출처 없는 수치, 원인을 현상에 섞기.
- **추천 프레임워크**: Fact–Interpretation 분리표, 사용자 여정 관찰, 5W1H.
- **AI 점검 관점**: 검증되지 않은 표현, 표본·출처 누락, 사실과 해석의 혼재.
- **포트폴리오 연결**: 관찰한 현상, 데이터와 출처, 불확실성.

### 3. `problem_definition` — 문제 정의

- **목적**: 해결할 핵심 문제와 의사결정 질문을 명확히 한다.
- **쉬운 설명**: 여러 현상 중 이번에 정말 답할 문제를 한 문장으로 좁히는 단계다.
- **핵심 질문**: 누구의 어떤 상황에서 어떤 목표가 막히는가? 왜 중요한가? 이번에 답할 질문은 무엇인가?
- **왜 필요한가**: 현상 목록만으로는 우선순위와 성공 기준을 정할 수 없다.
- **이전 단계와 관계**: `observation`의 사실과 정보 공백을 근거로 문제를 좁힌다.
- **다음 단계 산출물**: 사용자·상황·목표·마찰·영향이 포함된 문제 문장과 핵심 질문.
- **자주 발생하는 오류**: “앱 기능이 없다”처럼 해결안을 문제로 정의하기, 여러 문제를 한 문장에 묶기.
- **추천 프레임워크**: Problem Statement, How Might We, JTBD.
- **AI 점검 관점**: 사용자와 상황 누락, 해결안 편향, 관찰 근거와의 연결.
- **포트폴리오 연결**: 문제 정의, 문제의 중요성, 핵심 질문.

### 4. `problem_structuring` — 문제 분해·구조화

- **목적**: 핵심 문제를 겹치지 않는 하위 문제와 흐름으로 나눈다.
- **쉬운 설명**: 큰 문제를 살펴볼 수 있는 작은 조각과 관계로 펼치는 단계다.
- **핵심 질문**: 문제를 어떤 축으로 나눌 수 있는가? 누락·중복은 무엇인가? 우선 탐색할 영역은 어디인가?
- **왜 필요한가**: 큰 문제를 한 원인이나 한 기능으로 단정하는 것을 막는다.
- **이전 단계와 관계**: `problem_definition`의 한 문장을 검증 가능한 하위 구조로 펼친다.
- **다음 단계 산출물**: 문제 구조, 고객 여정 또는 issue tree, 우선 탐색 영역과 선택 이유.
- **자주 발생하는 오류**: 서로 다른 분해 기준 혼용, 해결안 목록을 문제 구조로 제시, MECE를 형식적으로 강요.
- **추천 프레임워크**: Issue Tree, Customer Journey Map, MECE, 시스템 맵.
- **AI 점검 관점**: 중복·누락, 분해 수준 불균형, 선택한 구조와 문제 문장의 불일치.
- **포트폴리오 연결**: 문제 구조, 분석 범위, 우선순위 근거.

### 5. `hypothesis` — 가설 설정

- **목적**: 가능한 원인과 결과 관계를 복수의 검증 가능한 문장으로 만든다.
- **쉬운 설명**: “왜 이런 일이 생겼을까?”에 대한 여러 설명을 시험 가능한 형태로 만드는 단계다.
- **핵심 질문**: 어떤 원인이 현상을 설명할 수 있는가? 대안 가설은 무엇인가? 무엇이 나오면 기각할 것인가?
- **왜 필요한가**: 첫 설명에 고착되지 않고 필요한 증거를 설계할 수 있다.
- **이전 단계와 관계**: `problem_structuring`의 우선 영역마다 가능한 설명을 만든다.
- **다음 단계 산출물**: 우선순위가 있는 복수 가설, 근거, 반증 조건.
- **자주 발생하는 오류**: 가설을 사실처럼 쓰기, 하나만 제시하기, 검증 불가능한 추상어 사용.
- **추천 프레임워크**: Hypothesis Tree, 인과 지도, Assumption Mapping.
- **AI 점검 관점**: 대안 가설 부족, 반증 조건 누락, 상관과 인과 혼동.
- **포트폴리오 연결**: 가설, 가설 선택 이유, 불확실성.

### 6. `evidence_validation` — 근거 수집·검증

- **목적**: 가설과 판단에 필요한 근거, 출처, 검증 방법과 한계를 정리한다.
- **쉬운 설명**: 내 설명이 맞는지 확인할 자료와 시험 방법을 정하고 결과의 한계를 적는 단계다.
- **핵심 질문**: 어떤 증거가 가설을 지지·기각하는가? 출처는 신뢰할 수 있는가? 결과의 한계는 무엇인가?
- **왜 필요한가**: 의견의 설득력을 증거의 양으로 착각하지 않고 검증 가능성을 높인다.
- **이전 단계와 관계**: `hypothesis`의 반증 조건을 실제 조사·실험 계획과 결과에 연결한다.
- **다음 단계 산출물**: 근거 목록, 출처, 검증 결과 또는 계획, 가설별 상태와 한계.
- **자주 발생하는 오류**: 지지 근거만 수집, 출처·시점 누락, 계획을 결과처럼 표현.
- **추천 프레임워크**: Evidence Matrix, 실험 설계, 출처 평가 체크리스트.
- **AI 점검 관점**: 근거와 주장 연결, 반대 증거 누락, 표본·측정·인과 한계.
- **포트폴리오 연결**: 근거와 검증, 사용한 방법, 한계.

### 7. `decision` — 대안 비교·의사결정

- **목적**: 복수 대안을 명시적 기준과 trade-off로 비교해 선택한다.
- **쉬운 설명**: 여러 선택지를 같은 기준으로 비교하고 무엇을 포기하는지까지 밝히는 단계다.
- **핵심 질문**: 가능한 대안은 무엇인가? 기준과 가중치는 무엇인가? 무엇을 포기하며 언제 재검토할 것인가?
- **왜 필요한가**: 익숙하거나 화려한 해결안을 자동 선택하지 않게 한다.
- **이전 단계와 관계**: `evidence_validation`의 가설 상태와 근거를 평가 기준에 반영한다.
- **다음 단계 산출물**: 대안, 비교 기준, 비교 결과, 선택과 보류 이유, 재검토 조건.
- **자주 발생하는 오류**: 대안 하나만 제시, 기준을 선택 후 맞추기, 불확실성 숨기기.
- **추천 프레임워크**: Decision Matrix, RICE·ICE 보조, Pre-mortem.
- **AI 점검 관점**: 비교 기준 편향, 누락 대안, 근거 없는 점수, 가역성.
- **포트폴리오 연결**: 대안 비교, 최종 결정, trade-off.

### 8. `solution_execution` — 해결안 설계·실행

- **목적**: 선택한 대안을 실행 가능한 작은 행동과 책임으로 구체화한다.
- **쉬운 설명**: 선택을 실제로 시험할 가장 작은 행동과 계획으로 바꾸는 단계다.
- **핵심 질문**: 무엇을 누구와 언제 실행하는가? 첫 검증 단위는 무엇인가? 위험과 대응은 무엇인가?
- **왜 필요한가**: 좋은 아이디어를 실행과 학습이 가능한 계획으로 전환한다.
- **이전 단계와 관계**: `decision`의 선택, 보류 조건과 trade-off를 설계 제약으로 사용한다.
- **다음 단계 산출물**: 해결안 범위, 단계별 행동, 담당·일정, 지표, 위험과 대응.
- **자주 발생하는 오류**: 거대한 한 번의 출시만 계획, 성공 지표 없이 할 일만 나열, 담당과 의존성 누락.
- **추천 프레임워크**: MVP Experiment, Action Plan, RACI, Pre-mortem.
- **AI 점검 관점**: 실행 가능성, 작은 검증 행동, 결정 기준과 지표의 연결.
- **포트폴리오 연결**: 해결안과 실행, 내 역할, 협업, 위험 관리.

### 9. `result_evaluation` — 결과 평가

- **목적**: 실행 결과 또는 예상 검증 결과를 기준과 비교하고 부작용·한계를 판단한다.
- **쉬운 설명**: 한 일을 성과라고 가정하지 않고 처음 정한 기준으로 무엇이 달라졌는지 보는 단계다.
- **핵심 질문**: 무엇이 달라졌는가? 목표와 비교하면 어떤가? 다른 설명과 부작용은 무엇인가?
- **왜 필요한가**: 실행 완료를 문제 해결로 착각하지 않고 학습을 남긴다.
- **이전 단계와 관계**: `solution_execution`에서 정한 지표와 관찰 계획을 평가 기준으로 사용한다.
- **다음 단계 산출물**: 결과 또는 측정 계획, 목표 대비 평가, 예상 밖 결과, 한계, 다음 판단.
- **자주 발생하는 오류**: 활동량을 성과로 표현, 데이터가 없는데 성과를 확정, 실패 정보를 숨김.
- **추천 프레임워크**: Before–After–Limit, 실험 회고, KPI/guardrail review.
- **AI 점검 관점**: 결과와 활동 구분, 기준 일관성, 대안 설명과 부작용.
- **포트폴리오 연결**: 결과 평가, 한계와 불확실성, 다음 개선.

### 10. `conclusion_reflection` — 결론 전달·회고

- **목적**: 문제부터 결과까지 핵심 논리를 전달하고 최초 생각과 최종 판단의 변화를 성찰한다.
- **쉬운 설명**: 결론을 설명하고 처음 생각이 왜 바뀌었는지 다음에 쓸 교훈으로 남기는 단계다.
- **핵심 질문**: 무엇을 결론으로 전달할 것인가? 무엇이 바뀌었고 왜 바뀌었는가? 다음 Case에 적용할 원칙은 무엇인가?
- **왜 필요한가**: 단순 요약을 넘어 사고 변화와 재사용 가능한 학습을 남긴다.
- **이전 단계와 관계**: 앞선 9단계의 근거, 결정, 실행과 평가를 하나의 추적 가능한 논리로 연결한다.
- **다음 단계 산출물**: 결론, 핵심 근거, 불확실성, 최초·최종 비교, 회고와 재사용 원칙.
- **자주 발생하는 오류**: 새로운 주장을 결론에서 추가, 한계 삭제, 결과만 미화, 회고를 감상으로 끝내기.
- **추천 프레임워크**: Pyramid Principle, What–So What–Now What, After Action Review.
- **AI 점검 관점**: 논리 연결, 근거 없는 결론, 변화 이유, 반대 의견에 대한 설명.
- **포트폴리오 연결**: 결론, 회고, 사용한 역량, 다음 개선 방향.

## 4. 단계 공통 산출물 계약 후보

각 단계는 최소한 다음 개념을 가질 수 있다. 정확한 필드와 필수 여부는 `03_V2_STAGE_TEMPLATES.md`와 `09_V2_DATA_MODEL.md`의 Open Decision이다.

- 자유 작성 초안
- 구조화 질문별 응답
- 사용한 프레임워크
- 근거·출처 참조
- AI 점검과 채택·거절
- 수정 버전과 checkpoint
- 완료 상태 및 완료 판단 근거
- 포트폴리오 섹션 연결
