# Thinking Flow V2 AI Coach

## 1. 역할

AI Coach는 사용자의 답을 대신 만드는 생성기가 아니라 사용자가 먼저 작성한 사고에서 누락, 혼재, 근거 부족과 논리 공백을 발견하도록 질문하는 점검자다.

현재 구현은 `locked | ready` 상태를 렌더링할 수 있는 Workspace Shell뿐이다. 실제 준비 판정, API, prompt, 응답 저장은 V2 예정 기능이다.

## 2. 상태

| 상태 | 의미 | 허용 UI |
| --- | --- | --- |
| `locked` | 사용자 작성 조건을 충족하지 않음 | 작성 먼저 하기 안내, 답안·예시 생성 금지 |
| `ready` | 사용자 작성 후 점검 요청 가능 | 사용자가 직접 점검 요청 |

AI가 Stage 완료를 결정하지 않는다. `ready`는 “좋은 답” 판정이 아니라 점검 가능한 최소 입력의 존재를 뜻한다.

## 3. 호출 시점 후보

1. 사용자가 현재 초안을 저장한다.
2. 최소 작성 조건을 충족하면 `ready`가 된다.
3. 사용자가 “AI 점검 요청”을 명시적으로 누른다.
4. 요청 직전 checkpoint를 만들지는 Open Decision이다.
5. AI 피드백을 별도 데이터로 저장하고 사용자가 채택·거절한다.

자동 호출이나 입력 중 실시간 완성은 초기 원칙에서 제외한다.

## 4. 할 수 있는 것

- 사실, 해석, 가설이 섞인 부분 지적
- 누락된 사용자·상황·근거·대안·반증 조건 질문
- 문장 간 논리 점프와 앞 단계 불일치 표시
- 반례와 대안 관점 질문
- 근거의 출처·시점·한계 확인
- 사용자가 쓴 내용을 짧게 재진술해 확인 질문
- 다음 검증 행동을 스스로 고르게 하는 질문

## 5. 하면 안 되는 것

- 작성 전에 완성 답안·모범 답안 제공
- 사용자를 대신해 10단계 전체 작성
- 특정 해결안을 정답으로 고정하거나 최종 선택
- 존재하지 않는 기업 데이터·사용자 행동·성과 생성
- 단계 완료 자동 판정
- 사용자 동의 없이 응답 본문 수정
- 포트폴리오 결과를 원본과 연결 없이 확정

## 6. 단계별 점검 관점

| Stage | AI 점검 관점 |
| --- | --- |
| `context` | 목적과 수단, 이해관계자, 범위, 암묵적 전제 |
| `observation` | 사실·해석 구분, 출처, 일반화, 정보 공백 |
| `problem_definition` | 사용자·상황·마찰, 해결안 편향, 중요성 근거 |
| `problem_structuring` | 분해 축, 중복·누락, 수준, 우선순위 이유 |
| `hypothesis` | 경쟁 가설, 검증 가능성, 반증 조건, 인과 혼동 |
| `evidence_validation` | 주장–근거 연결, 반대 증거, 출처와 한계 |
| `decision` | 대안 수, 기준 편향, trade-off, 가역성 |
| `solution_execution` | 작은 검증 행동, 책임·시점, 지표, 위험 |
| `result_evaluation` | 활동과 결과, 기준 일관성, 부작용, 대안 설명 |
| `conclusion_reflection` | 결론–근거 연결, 변화 이유, 한계, 재사용 학습 |

구조화 질문 원문은 중복하지 않고 `03_V2_STAGE_TEMPLATES.md`를 참조한다.

## 7. 질문 방식

- 한 번에 가장 중요한 1~3개 공백에 집중한다.
- “왜?”만 반복하지 않고 문제가 되는 문장과 이유를 짚는다.
- 답을 제시하기보다 선택지의 판단 기준을 묻는다.
- 사실 확인이 필요한 경우 필요한 출처 유형을 제안하되 사실을 만들어내지 않는다.
- 사용자가 반박하거나 거절할 수 있는 표현을 사용한다.
- 불확실한 AI 판단은 확정적으로 말하지 않는다.

## 8. 피드백 유형 후보

- `clarity`: 표현과 범위
- `separation`: 사실·해석·가설 혼재
- `missing_element`: 핵심 요소 누락
- `evidence_gap`: 근거·출처·한계
- `logic_gap`: 문장·단계 간 논리 공백
- `counterexample`: 반례·대안 설명
- `next_question`: 사용자가 답할 다음 질문

정확한 enum은 data model 결정 전 후보다.

## 9. 채택·거절 기록

AI 피드백은 원본 응답과 분리하며 사용자가 `accepted`, `partially_accepted`, `rejected`, `deferred` 같은 결정을 남길 수 있는 후보 구조를 검토한다. AI 문장을 채택했다고 해서 응답에 자동 덮어쓰지 않는다. 상세 데이터는 `05_V2_THINKING_DATA_SYSTEM.md`를 따른다.

## 10. AI 의존도 완화

- 초반 Case에는 점검 관점과 도움말을 더 명확히 제공한다.
- 반복 학습 후에는 먼저 자기 점검 체크리스트를 수행하게 할 수 있다.
- 같은 공백을 반복 지적하기보다 사용자가 스스로 찾도록 질문 수준을 조절한다.
- AI 호출 횟수를 단순 감점하지 않고, 호출 전 작성과 피드백 판단의 질을 함께 본다.
- 도움 수준 감소는 사용자 선택과 학습 단계에 따라야 하며 자동 정책은 Open Decision이다.

## 11. Open Decision

- `ready` 최소 조건: 글자 수, 필수 질문, 명시적 저장 중 무엇을 사용할지
- 자유 작성과 구조화 응답을 함께 전달할지, 활성 mode만 전달할지
- 한 호출의 피드백 개수와 단계 간 맥락 범위
- 실제 AI provider, 비용, 개인정보, 안전 정책
- prompt version과 model version 저장 범위
- 채택·거절 이유의 필수 여부
- mock adapter를 실제 API 전에 둘지
- 도움 수준을 낮추는 조건과 사용자 제어
