# Thinking Flow V2 Portfolio System

## 1. 목적

Portfolio System은 10단계 사고 기록을 결과물로 재구성하되, 보기 좋은 최종 문장만 남기지 않는다. 모든 파생 섹션은 가능한 한 원본 Stage, FieldResponse와 ResponseVersion으로 돌아갈 수 있어야 한다.

현재 V1에는 포트폴리오 관련 후보 타입이 일부 있을 수 있으나, 아래 V2 사용자 흐름과 변환 시스템은 구현되지 않았다.

## 2. Case Summary/Report와 Portfolio의 분리

- **Case Summary/Report**는 사용자가 10단계 전체 논리, 미완성 항목과 불확실성을 검토하는 내부 학습 산출물이다.
- **Portfolio**는 외부 설명을 위해 사용자가 선택하고 편집한 파생 결과물이다.
- Portfolio는 Case Summary를 그대로 복사하거나 자동 공개하지 않는다.
- 실제 역할, 실행 여부, 성과와 수치는 사용자의 원본 입력 없이는 생성하거나 추론하지 않는다.

## 3. 생성 조건 후보

- 최소한 핵심 Stage의 원본 응답이 저장되어 있다.
- 결과가 실제인지 계획인지 명확히 구분되어 있다.
- 공개 가능한 출처와 민감 정보가 검토되었다.
- 사용자가 포트폴리오 생성을 명시적으로 요청한다.
- 자동 변환 후 사용자가 각 섹션을 검토·수정한다.

10단계 완료를 반드시 요구할지, 일부 Stage로 초안을 허용할지는 Open Decision이다.

## 4. Case 포트폴리오 구조

| 포트폴리오 섹션 | 주요 원본 |
| --- | --- |
| Case 개요 | PracticeCase, `context` |
| 배경과 목적 | `context` |
| 관찰한 현상 | `observation` |
| 문제 정의 | `problem_definition` |
| 문제 구조 | `problem_structuring` |
| 가설 | `hypothesis` |
| 근거와 검증 | `evidence_validation` |
| 대안 비교·최종 결정 | `decision` |
| 해결안과 실행 | `solution_execution` |
| 결과 평가 | `result_evaluation` |
| 한계와 불확실성 | `evidence_validation`, `result_evaluation` |
| 결론과 회고 | `conclusion_reflection` |
| 내 역할·사용한 역량 | `context`, `solution_execution`, 사용자 편집 |
| 다음 개선 방향 | `result_evaluation`, `conclusion_reflection` |

## 5. 자동 변환 원칙

- 변환 결과는 원본이 아니라 파생 artifact다.
- 원본에 없는 성과, 역할, 수치, 인과를 생성하지 않는다.
- 사용자의 직무나 역할은 Case 맥락만으로 자동 추론하지 않는다.
- “계획”, “가상 검증”, “실제 실행 결과”를 구분한다.
- 출처와 불확실성을 유지한다.
- 섹션별로 사용한 원본 버전을 기록한다.
- 원본 변경 후 artifact가 오래된 상태임을 표시할 수 있어야 한다.

## 6. 사용자 수정

사용자는 제목, 강조 순서, 설명 문장과 공개 범위를 편집할 수 있다. 수정한 포트폴리오 문장도 버전을 가질 수 있으나, 원본 사고 기록을 수정하지 않는다. 원본과 다른 해석을 추가할 때 출처 상태를 표시하는 방안을 검토한다.

## 7. 포트폴리오 유형

### Case별 포트폴리오

한 문제의 사고 과정과 판단 변화를 보여준다. V2 첫 구현 후보로 가장 좁은 범위다.

### 역량 포트폴리오

여러 Case에서 반복된 강점, 취약점, 성장 변화와 대표 근거를 묶는다. metric의 신뢰성과 Case 비교 가능성 검증이 선행되어야 한다.

### 직무별 변환

PM, 데이터 분석, 서비스 기획 등 직무에 따라 강조 순서와 용어를 조정한다. 원본에 없는 직무 경험을 만들어내지 않는다.

### 기술 블로그 변환

문제–탐색–검증–학습의 서사로 재구성한다. 공개 출처와 개인정보를 다시 검토한다.

### 면접 답변 변환

제한 시간에 맞춘 요약과 예상 후속 질문을 만든다. STAR 같은 형식은 표현 프레임일 뿐 원본 사실을 대체하지 않는다.

## 8. 원본 연결

`PortfolioSection` 후보는 다음을 참조한다.

- 원본 `ThinkingCase`와 Stage
- 하나 이상의 `FieldResponse`
- 사용된 `ResponseVersion`
- 근거 `SourceReference`
- 마지막 동기화 시점과 stale 상태

정확한 관계는 `09_V2_DATA_MODEL.md`에서 확정 전 후보로 관리한다.

## 9. 공개·비공개

- 기본 상태를 비공개로 할지 Open Decision으로 둔다.
- 섹션별 공개 여부와 전체 artifact 공개 여부를 구분한다.
- 원본 사고 기록은 포트폴리오 공개만으로 자동 공개되지 않는다.
- 기업명, 개인 정보, 내부 자료, AI 대화 포함 여부를 게시 전 확인한다.
- 공유 링크 철회와 export 후 통제 한계를 설명한다.

## 10. Open Decision

- 생성에 필요한 최소 완료 Stage와 결과 상태
- 자동 생성과 템플릿 기반 조합 중 첫 구현 방식
- 원본 변경 시 자동 재생성, 수동 동기화, diff 제공 중 선택
- 포트폴리오 본문 자체의 버전 정책
- 직무 템플릿의 종류와 검수 책임
- 공개 기본값, 공유 링크, export format
- 다수 Case 역량 분석을 사용자에게 설명하는 방식
