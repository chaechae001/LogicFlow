# 1. 프로젝트 한 문장 정의

**Thinking Flow는 사용자가 자신의 생각을 먼저 꺼내고, 논리적 사고 절차에 따라 반복적으로 훈련하며, 사고 과정과 수정 이력을 데이터로 축적해 분석·시각화·리포트·포트폴리오로 전환하는 웹 기반 사고 학습 플랫폼이다.**

이 서비스는 단순한 사고 정리 도구, 프롬프트 모음, AI 답변 생성기, 자동 포트폴리오 생성기가 아니다.

핵심 목적은 다음과 같다.

> 처음에는 가이드가 있어야 생각할 수 있었던 사용자가, 반복 훈련 후에는 가이드가 줄어들어도 스스로 문제를 정의하고, 구조화하고, 가설을 세우고, 근거를 검토하고, 대안을 비교하고, 결론을 도출할 수 있도록 사고법을 내재화한다.

---

# 2. 프로젝트를 시작한 배경

AI 기술이 빠르게 발전하면서 단순 지식 검색, 문서 생성, 데이터 요약은 점차 기본 역량이 된다.

따라서 같은 AI를 사용하더라도 다른 결과를 만드는 핵심은 다음과 같은 인간의 근원적 역량에 있다고 보았다.

- 문제의 본질을 질문하는 능력
- 현상과 원인을 구분하는 능력
- 관찰, 해석, 가설, 해결안을 분리하는 능력
- 복잡한 문제를 구조화하는 능력
- 가설을 만들고 검증하는 능력
- 근거와 불확실성을 함께 다루는 능력
- 여러 대안을 비교해 판단하는 능력
- 새로운 환경과 도메인에 사고법을 전이하는 능력
- AI를 상황에 맞게 조합하고 지휘하는 능력
- 자신의 보이지 않는 사고 과정을 외부에 증명하는 능력

사용자는 AI를 단순히 잘 쓰는 사람이 아니라, AI가 바뀌어도 이를 잘 활용하고 새로운 시스템과 사회를 설계할 수 있는 사람으로 성장하고자 한다.

# 3. 해결하려는 핵심 사용자 문제

## 3.1 표면 문제

- 머릿속에 생각은 많지만 글로 꺼내기 어렵다.
- 어디서부터 어떻게 생각해야 하는지 모른다.
- 문제, 원인, 가설, 해결책이 한꺼번에 섞인다.
- MECE, 5Why, SCQA 같은 프레임워크를 배워도 실제 문제에 적용하기 어렵다.
- AI가 만든 결과는 그럴듯하지만 자신의 사고로 남지 않는다.
- 프로젝트 결과는 있지만 사고 과정을 설명하거나 증명하기 어렵다.
- 채팅, 노트, 문서에 기록이 흩어져 사고의 발전 과정을 확인하기 어렵다.
- 논리적 사고력이 실제로 성장하고 있는지 측정하기 어렵다.
- 자료 정리에 집중하다 실제 학습과 내재화가 약해지는 문제가 있다.

## 3.2 근본 문제

> 사람들은 생각이 없는 것이 아니라, 생각을 밖으로 꺼내고 검토하고 수정하며 축적할 수 있는 반복 가능한 사고 구조를 갖고 있지 않다.

서비스가 해결해야 하는 핵심은 다음 세 가지다.

```text
1. 사고 시작의 어려움
2. 사고 구조의 부재
3. 사고 과정의 휘발
```

# 4. 사용 전후 변화

## 사용 전

```text
막연한 생각
→ AI에게 질문
→ 완성된 답변 수령
→ 일부 수정
→ 문서 저장
→ 사고 과정은 남지 않음
→ 다음 문제에서 다시 AI 의존
```

## 사용 후

```text
관찰·생각 자유 기록
→ 자신의 언어로 최초 답변 작성
→ 사실·해석·가설·질문·해결 아이디어 분리
→ 문제와 맥락 정의
→ 문제 분해 및 구조화
→ 여러 가설 생성
→ 근거·데이터·반례 검토
→ 대안 비교 및 판단
→ 실행안 설계
→ 결과 평가
→ 결론과 회고
→ 사고 변화 시각화
→ Thinking Case 저장
→ 리포트 및 포트폴리오 전환
→ 다음 사례에 사고법 재사용
```

# 6. 제품의 3개 핵심 시스템

## A. Thinking Learning System

논리적 사고를 배우고 반복 훈련하는 영역.

주요 기능:

- 사고 프레임워크 추천

- 가이드 강도 조절
- 반복 훈련
- 실제 업무·서비스·데이터 문제 기반 Case

## B. Thinking Data System

사고 과정과 성장 데이터를 기록·분석하는 영역.

주요 기록:

- 최초 작성
- 각 단계 답변
- 수정 전후 버전
- AI 질문
- 사용자가 채택·거절한 제안
- 가설 변화
- 사용한 근거
- 판단 기준
- 최종 결론
- 회고
- 단계별 소요 시간
- 반복 훈련에 따른 변화
- 자주 발생하는 논리적 공백
- 강점·약점 패턴

## C. Thinking Portfolio System

축적된 사고 데이터를 외부에 보여주는 영역.

포트폴리오는 단순 결과물 전시가 아니라 다음을 증명해야 한다.

- 어떤 상황을 관찰했는가
- 무엇을 사실로 보았고 무엇을 해석으로 보았는가
- 처음에 어떤 문제로 이해했는가
- 어떤 질문과 가설을 만들었는가
- 어떤 근거로 사고를 수정했는가
- 어떤 대안을 비교했는가
- 무엇을 선택했고 왜 선택했는가
- 초기 사고와 최종 사고가 어떻게 달라졌는가
- 다음 Case에 적용할 수 있는 원리는 무엇인가

# 8. 공통 사고 FLOW

## 8.1 10단계 학습 모델

```text
① 목적·맥락 이해
        ↓
② 현상 관찰
        ↓
③ 문제 정의
        ↓
④ 문제 분해·구조화
        ↓
⑤ 가설 설정
        ↓
⑥ 근거 수집·검증
        ↓
⑦ 대안 비교·의사결정
        ↓
⑧ 해결안 설계·실행
        ↓
⑨ 결과 평가
        ↓
⑩ 결론 전달·회고
        ↺
   새로운 문제 정의
```

## 8.2 기존 8단계 구현 구조

초기 개발 문서와 구현은 다음 8단계를 사용했다.

```text
1. 사실·해석 분리
2. 문제 정의
3. 고객 여정 구조화
4. 원인 가설
5. 검증 설계
6. 대안 비교
7. Action Plan
8. 결론·회고
```

## 8.3 현재 권장 방향

**학습 모델은 10단계로 유지하고, MVP Workspace 화면은 8개로 통합할 수 있다.**

예시:

```text
화면 1. 목적·맥락 + 최초 생각
화면 2. 현상 관찰 + 사실·해석 분리
화면 3. 문제 정의
화면 4. 문제 분해·구조화
화면 5. 가설 설정
화면 6. 근거 수집·검증
화면 7. 대안 비교 + 해결안·실행 계획
화면 8. 결과 평가 + 결론·회고
```

중요:

- 10단계는 학습 개념 모델이다.
- 8개 화면은 MVP UX 압축 구조다.
- 화면 수 때문에 학습 단계의 의미가 사라져서는 안 된다.
- 최종 확정 전 `01_THINKING_FLOW.md`, `05_MVP_PRD.md`, `06_DECISION_LOG.md`에 명시해야 한다.

# 9. 단계별 핵심 질문과 산출물

## 1. 목적·맥락 이해

핵심 질문:

- 지금 해결하려는 목표는 무엇인가?
- 왜 이 문제를 다루는가?
- 왜 지금 중요한가?
- 누구에게 중요한가?
- 조직·프로젝트 목표와 어떻게 연결되는가?
- 이해관계자는 누구인가?
- 어떤 제약이 있는가?
- 현재 내가 맡은 역할은 무엇인가?

산출물:

- 상황
- 목표
- 대상
- 이해관계자
- 제약
- 지금 해결해야 하는 이유
- 핵심 의사결정 질문

## 2. 현상 관찰

핵심 질문:

- 실제로 어떤 현상이 발생했는가?
- 누가, 언제, 어떤 상황에서 문제를 겪는가?
- 직접 관찰 가능한 행동과 수치는 무엇인가?
- 사용자 피드백과 데이터에서 어떤 패턴이 보이는가?
- 사실과 해석을 구분했는가?

산출물:

- 관찰된 사실
- 사용자 행동
- 정량 지표
- 정성 피드백
- 아직 확인되지 않은 해석

예:

```text
관찰된 현상:
결제 전 이탈률이 증가했다.

추정 원인:
결제 단계가 복잡해졌을 가능성이 있다.
```

## 3. 문제 정의

핵심 질문:

- 해결해야 할 핵심 문제는 무엇인가?
- 누구의 어떤 문제가 중요한가?
- 증상과 문제를 혼동하지 않았는가?
- 원인이나 솔루션을 문제 문장에 미리 넣지 않았는가?
- 문제가 해결되면 어떤 변화가 일어나야 하는가?

권장 문제 정의 문장:

```text
[누가] [언제/어떤 맥락에서] [무엇을 하려다가]
```

# 10. 자유 작성과 구조화 질문의 관계

이 서비스는 처음부터 빈칸형 논리 폼에 답하게 하는 서비스가 아니다.

권장 흐름:

```text
자유 작성
→ 사용자가 직접 분류
→ 구조화 질문
→ AI의 논리적 공백 점검
→ 사용자 수정
→ 버전 저장
```

첫 화면 예시:

```text
지금 떠오르는 생각을 자유롭게 적어보세요.

완성된 문장이 아니어도 됩니다.
관찰한 것, 궁금한 것, 불편한 것,
떠오른 아이디어를 그대로 적어보세요.
```

사용자 작성 후 분류 대상:

- 직접 관찰한 사실
- 나의 해석
- 아직 확인되지 않은 가설
- 궁금한 질문
- 떠오른 해결 아이디어

중요 원칙:

- 질문은 답을 유도하기보다 사고의 공백을 발견하게 해야 한다.
- 한 화면에 너무 많은 질문을 한꺼번에 노출하지 않는다.
- 메인 질문과 펼쳐 보는 보조 질문을 구분한다.
- 사용자가 왜 이 질문에 답하는지 학습 목적을 알려준다.
- AI는 사용자 작성 전 답이나 예시를 먼저 주지 않는다.
- 예시가 필요하더라도 사용자가 도움을 요청한 뒤 최소 범위로 제공한다.
- 사용자가 처음 떠올린 해결 아이디어는 삭제하지 않되, 문제 정의와 분리해 보관한다.

# 11. AI의 역할

## 11.1 AI가 해야 하는 것

- 사용자의 사고를 대신하지 않고 질문한다.
- 사실과 해석이 섞인 부분을 표시한다.
- 문제 정의에 해결책이 포함됐는지 점검한다.
- 빠진 대상, 맥락, 지표, 근거를 알려준다.
- 가설이 검증 가능한 문장인지 확인한다.
- 경쟁 가설과 반례를 질문한다.
- 논리적 비약을 보여준다.
- 대안 비교 기준이 불명확한 부분을 짚는다.
- 근거 수준과 불확실성을 구분한다.
- 단계 산출물이 다음 단계에 연결되는지 확인한다.
- 사용자가 쓴 문장과 수정 문장의 차이를 보여준다.
- 반복 학습 데이터를 바탕으로 자주 발생하는 사고 패턴을 알려준다.
- 적절한 사고 프레임워크를 추천하되 적용을 강제하지 않는다.
- 데이터 분석 Case에서는 검증 설계와 분석 방법을 지원한다.

## 11.2 AI가 하면 안 되는 것

- 처음부터 완성된 문제 정의를 작성한다.
- 사용자의 해결책을 정답처럼 확정한다.
- 근거 없이 기업 내부 상황이나 사용자 행동을 사실처럼 단정한다.
- 사용자의 최초 답변을 덮어쓴다.
- AI 제안을 자동 채택한다.
- “좋은 아이디어입니다” 같은 일반적 칭찬만 제공한다.
- 여러 단계의 답을 한 번에 대신 완성한다.
- 문제 정의 전에 솔루션 아이디어를 중심으로 흐름을 끌고 간다.
- 포트폴리오를 미화하거나 검증되지 않은 성과를 추가한다.

## 11.3 권장 AI 피드백 예시

```text
현재 문장에는 대상 사용자가 없습니다.

관찰된 현상과 추정 원인이 한 문장에 섞여 있습니다.

이 가설이 틀렸다고 판단할 기준이 아직 없습니다.

제시한 결론을 지지하는 근거가 하나뿐이며,
다른 설명 가능성을 배제하지 못했습니다.

대안의 평가 기준이 명시되지 않아
왜 이 안을 선택했는지 비교하기 어렵습니다.
```

# 14. 데이터 분석 및 ML 확장

서비스는 일반 논리적 사고 훈련이 중심이며, 데이터 분석 Case에서는 다음 자료의 원칙을 선택적으로 적용한다.

## 기준 자료 역할

- **DSUR**: 통계 개념, 연구 질문, 가정 검토, 효과크기, 해석
- **ISLP**: 통계 학습, 예측 모델링, 모델 평가, 교차검증, 머신러닝
- **FDV**: 데이터 유형에 맞는 시각화, 불확실성, 시각적 오해 방지
- **LADR**: 벡터공간, 선형변환, 고유값, SVD 등 구조적 이해
- **Minto Pyramid Principle**: 결론과 근거의 위계, 문제 정의와 전달
- **Feature Engineering for Machine Learning**: 데이터와 모델 맥락에 맞는 특징 설계
- **SHAP**: 복잡한 모델 예측의 해석
- **Bayesian Optimization**: 평가 비용이 큰 블랙박스 최적화
- **XGBoost / TabNet / Transformer / LSTM / EfficientNet / ViT / AlexNet**: 관련 분석 Case에서 모델 구조와 선택 근거를 학습할 때 참고

주의:

- 모든 Case에 통계 가설과 머신러닝을 강제하지 않는다.
- 비즈니스 문제의 성격과 데이터 존재 여부에 따라 선택한다.
- 모델 정확도뿐 아니라 문제 정의, 데이터 적합성, 해석 가능성, 검증 설계를 함께 본다.
- p-value 하나로 결론을 내리지 않는다.
- 데이터 분석 결과 역시 사용자의 사고 과정과 연결해야 한다.
- 시각화는 장식이 아니라 비교, 분포, 관계, 추세, 불확실성을 명확히 전달해야 한다.

## 15.2 현재 대표 Case: 올리브영 O2O

주의: 아래 내용은 연습용 가설적 문제 상황이며, 검증된 올리브영 내부 데이터나 공식 사실로 단정하지 않는다.

### 앱 이용 관점

현상 가정:

- 세일 기간이나 픽업 서비스 이용 시 앱 사용이 집중된다.
- 평소에는 방문 목적이 제한적일 수 있다.

문제 정의 후보:

- 명확한 쇼핑 목적이 없는 시점에 고객이 머무르거나 다시 방문할 이유가 충분하지 않아 일상적 재방문이 제한될 가능성이 있다.

### 입점 브랜드 관점

현상 가정:

- 대형 세일 기간과 비시즌의 매출 편차가 클 수 있다.

문제 정의 후보:

- 비시즌에 고객의 탐색과 구매 전환을 지속시키는 앱 내 검색·콘텐츠·브랜드 발견 구조가 충분하지 않을 가능성이 있다.

### O2O 관점

현상 가정:

- 고객이 오프라인 매장에서 테스트한 후 타사 온라인 채널에서 구매할 수 있다.

문제 정의 후보:

- 오프라인 체험이 올리브영 온라인 혜택, 리뷰, 재고, 오늘드림 구매로 자연스럽게 이어지는 동선이 직관적이지 않을 가능성이 있다.

## 15.3 Case 시작 시 최초 입력

Task 03에서 구현된 최초 입력은 다음 세 가지다.

- 내 첫 생각
- 이미 떠오른 해결안
- 이 Case의 핵심 의사결정 질문

향후 개선 방향:

- `이미 떠오른 해결안`은 삭제하지 않고 별도 보관한다.

# 18. 포트폴리오 시스템

## 18.1 포트폴리오의 목적

포트폴리오는 “예쁜 결과물”이나 “정답을 맞힌 결과”를 보여주는 것이 아니다.

다음을 증명한다.

- 문제를 어떻게 발견했는가
- 처음에 무엇을 놓쳤는가
- 어떤 질문이 사고를 바꿨는가
- 어떻게 문제를 재정의했는가
- 어떤 근거를 검토했는가
- 어떤 가설을 버렸는가
- 어떤 트레이드오프를 고려했는가
- 왜 최종 결정을 내렸는가
- 무엇을 학습했고 다른 문제에 어떻게 적용할 수 있는가

## 18.2 포트폴리오 구성 예시

```text
1. Case 개요
2. 상황과 목표
3. 최초 생각
4. 관찰 사실과 초기 해석
5. 문제 정의의 변화
6. 문제 구조와 Logic Flow
7. 가설 목록과 우선순위
8. 검증 설계와 근거
9. 대안 비교와 의사결정
10. 실행 계획
11. 결과 평가
12. 초기·최종 사고 비교
13. AI와 사용자의 역할 구분
14. 회고와 전이 가능한 원리
15. 남은 불확실성
```

## 18.3 외부 공개 시 주의

- 검증되지 않은 기업 내부 지표를 사실처럼 쓰지 않는다.
- 실제 데이터가 없으면 가설, 시뮬레이션, 제안임을 명확히 표시한다.
- AI가 만든 문장과 사용자의 판단을 구분한다.
- 성과를 과장하지 않는다.
- 출처와 근거 수준을 표시한다.

# 19. 사고 Flow 시각화

사용자는 자신의 사고 과정을 도식화해서 보고 싶어 한다.

가능한 시각화:

- 단계별 Timeline
- Observation → Interpretation → Hypothesis → Evidence → Decision 연결도
- Problem Tree / Logic Tree
- 가설과 검증 근거 연결
- 대안 비교 Matrix
- 초기 문제 정의와 최종 문제 정의 비교
- 수정 버전 Diff
- AI 질문이 사고에 미친 영향
- Case별 반복 패턴
- 역량 Radar 또는 성장 추세
- 자주 발생하는 논리 오류
- 포트폴리오용 사고 여정 Map

주의:

- 시각화 자체가 사고를 대신하면 안 된다.
- 사용자가 작성한 데이터를 기반으로 생성한다.
- 연결 관계를 AI가 임의로 확정하지 않고 사용자가 수정할 수 있어야 한다.
- 단순한 예쁜 그래프보다 사고 변화가 이해되도록 설계한다.

# 40. 최종 핵심 요약

Thinking Flow의 핵심은 다음 한 줄이다.

> **AI가 답을 만드는 서비스가 아니라, 사용자가 자신의 생각을 꺼내고 검토하고 수정하고 축적하면서 논리적 사고법을 내재화하고, 그 과정을 증명 가능한 데이터와 포트폴리오로 만드는 서비스다.**

따라서 모든 기능과 구현 결정은 다음 질문으로 평가한다.

```text
이 기능이 사용자의 사고를 대신하는가,
아니면 사용자가 더 잘 생각하도록 돕는가?

이 기능이 최종 답만 남기는가,
아니면 사고 변화 과정을 보존하는가?

이 기능이 예쁜 결과물을 만드는가,
아니면 사용자의 문제 정의와 판단 근거를 증명하는가?

이 기능이 AI 의존을 높이는가,
아니면 반복할수록 사용자의 독립성을 높이는가?
```
