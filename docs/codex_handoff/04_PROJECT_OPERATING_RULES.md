# Thinking Flow 프로젝트 운영 원칙

> 이 문서는 `AGENTS.md`, `docs/DECISION_LOG.md`, `docs/03_LEAN_PRD.md`, `docs/02_PRODUCT_CORE.md`를 대체하지 않는다. 충돌 시 `00_START_HERE.md`의 우선순위를 따른다.

## 1. 작업 원칙

- 코드 수정 전에 실제 Git 상태와 기준 문서를 확인한다.
- 과거 채팅 기억보다 저장소의 파일과 Git 상태를 우선한다.
- 문서가 충돌하면 임의로 화해시키지 말고 충돌을 보고한다.
- 사용자의 승인 없이 Task 범위를 확장하지 않는다.
- 검토만 요청받은 경우 파일을 수정하지 않는다.

## 2. 제품 원칙

- 사용자가 AI보다 먼저 작성한다.
- AI는 완성 답안을 먼저 제공하지 않는다.
- 관찰, 해석, 가설, 해결안을 구분한다.
- 결과뿐 아니라 사고 과정과 수정 이력을 보존한다.
- 도움은 반복 훈련에 따라 점차 줄어들 수 있어야 한다.
- 포트폴리오는 결과물 전시가 아니라 사고 과정의 증거다.

## 3. 최신 구조 원칙

- 학습 FLOW, Workspace, CaseStep은 10단계로 운영한다.
- 10단계를 8개 단계로 축약하지 않는다.
- 각 단계에서 자유 작성과 구조화 입력 중 하나를 선택할 수 있다.
- 두 작성 방식은 동일한 CaseStep에 속한다.
- 작성 방식을 바꾸거나 함께 사용해도 기존 데이터는 삭제하지 않는다.
- 사용자 작성 전 AI Coach는 비활성이다.
- 단계 이동과 완료는 별개다.
- Soft Gate는 경고하되 이동을 강제로 차단하지 않는다.

## 4. Task 범위 원칙

### Task 04

- Shell, 내비게이션, 단계 상태, 작성 방식 선택 UI, AI 상태, Soft Gate
- 10단계 타입과 route 정렬
- 실제 입력 기능이 들어갈 구조 준비

### Task 05 이후

- 실제 입력 CRUD
- 저장·자동 저장·버전 생성
- AI 점검
- 완료 판정
- 버전 비교

## 5. Git 원칙

- 분석 단계에서 add, commit, push를 실행하지 않는다.
- `git add -A`를 사용하지 않는다.
- 사용자가 승인한 Task 관련 파일만 경로를 명시해 staging한다.
- 커밋 전 lint, typecheck, test, build를 실행한다.
